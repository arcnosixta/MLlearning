# PostgreSQL: хранение, запросы и перенос данных

Цель: различать логический перенос базы и перенос файлов кластера, а также доказывать восстановимость резервной копии.

## Клиент и сервер

psql — клиент, PostgreSQL server хранит данные и выполняет запросы. Linux-пользователь postgres и роль базы данных — разные сущности, даже если имена совпадают. В учебной VM выясни версию сервера, адрес подключения и список баз; используй `psql -X -d training`, чтобы личный psqlrc не менял поведение сценария. Команда `SELECT current_database(), current_user;` подтверждает, куда ты попал. Перед любым изменением проверяй этот контекст.

SQL различает структуру и строки. CREATE TABLE задаёт ограничения, INSERT/UPDATE/DELETE меняют данные, SELECT читает. Транзакция BEGIN/COMMIT объединяет изменения; ROLLBACK отменяет незавершённую группу. Для учебных запросов создай отдельную базу и роль с минимальными правами. Не выдавай superuser обычному приложению ради устранения любой ошибки доступа. В скриптах psql задавай `-v ON_ERROR_STOP=1`, иначе отдельный SQL-сбой может не остановить всю последовательность так, как ты ожидаешь.

## Логическая резервная копия

`pg_dump -Fc -d training -f training.dump` создаёт custom-format архив одной базы. Версия клиента и поддерживаемая версия сервера должны быть совместимы. Роли и прочие глобальные объекты не входят в обычный dump одной базы: их миграцию планируют отдельно. `pg_restore --list training.dump` проверяет состав, но не доказывает успешное восстановление. Создай отдельную пустую базу и выполни `pg_restore --exit-on-error --single-transaction -d training_restore training.dump`, учитывая требования расширений, владельцев и прав.

Проверь не только код завершения: сравни число строк, контрольные агрегаты, ограничения, права и запросы приложения. Снимок pg_dump внутренне согласован, но резервная копия всей системы может требовать согласования с файлами приложения. Пароли передавай через безопасно настроенную аутентификацию и конфигурацию клиента, а не записывай в публичную команду с URL.

## Физическое размещение и rsync

Перенос каталога данных требует знания конкретной версии, tablespaces, WAL, владельца, режима доступа и конфигурации. Простое копирование живого каталога через rsync не становится согласованной резервной копией. Для физического резервирования используй штатный протокол, например pg_basebackup, либо документированный остановленный перенос. В VM сохрани рабочую копию и конфиги, проверь новый mount, свободное место и устойчивый идентификатор файловой системы. Не переключай приложение до проверки нового сервера. Для переноса между версиями изучай pg_upgrade или логический dump/restore, не подменяя их переименованием директории.
