# Bash: обработка ошибок, errexit и nounset

Цель: делать отказ заметным, не продолжать опасную последовательность после ошибки и не полагаться на один «магический» набор флагов.

## Код завершения как контракт

Успешная команда возвращает 0, неуспешная — ненулевой код. if, && и || используют этот статус. Сразу сохраняй нужный код, потому что printf, присваивание и любая следующая команда могут его заменить. Для ожидаемого отказа, например «запись не найдена», выбери отдельную обработку. Не превращай все ошибки в успех через `|| true`: тогда отсутствие файла, неверные права и отказ диска выглядят одинаково безобидно.

Операцию с последствиями разбей на подготовку, проверку и применение. Сначала сформируй новый конфиг во временном файле, проверь синтаксис, затем замени рабочий и проверь сервис. Если команда не поддерживает транзакцию, сценарий должен знать, какие шаги уже выполнены и как откатить каждый. Лог с текстом «готово» не должен появляться до последней проверки результата.

## set -e не универсальная страховка

errexit завершает shell при некоторых неперехваченных неуспешных командах. Но исключения контекстные: проверки if/while, части &&/||, инверсия ! и отдельные компоненты pipeline могут менять поведение. Особенно важно, что функция, вызванная как проверка условия, не обязательно ведёт себя так же, как прямой вызов. Поэтому внутри функции с изменениями используй явные проверки критических команд и осмысленный return, а не ожидание, что set -e исправит любой сценарий.

Без pipefail статус pipeline обычно соответствует последней команде. `producer | consumer` может выглядеть успешным, если producer сломался, а consumer нормально обработал EOF. `set -o pipefail` меняет итоговый статус на ненулевой статус правого неуспешного участника. Для подробностей есть массив PIPESTATUS; копируй его сразу после pipeline. Даже pipefail не задаёт политику частично выполненных изменений.

## set -u и допустимое отсутствие

nounset считает обращение к неназначенной переменной ошибкой во многих обычных раскрытиях. Пустая назначенная строка при этом не равна отсутствующей переменной. Для опциональной настройки подойдёт `${name:-default}`, для обязательной — `${name:?понятное сообщение}`; двоеточие заставляет учитывать и пустоту. При передаче аргументов проверь $# до чтения $1. Разделяй секрет и текст диагностики: ошибка конфигурации не должна печатать пароль.

## Trap и проверяемость

ERR trap помогает централизовать диагностику, но имеет собственные исключения и правила наследования; он не заменяет все явные проверки. EXIT trap используй для уборки своих ресурсов с сохранением исходного статуса. Тестируй сценарий с намеренным отказом посередине, отсутствующим аргументом и неуспешным первым компонентом pipeline. Запускай сначала в отдельной VM или временной области, а системные изменения — только после проверки плана отката. Для синтаксиса полезен `bash -n script.sh`, но он не проверяет смысл команд.
