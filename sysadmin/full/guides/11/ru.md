# DHCP, TFTP и DNS/BIND

Цель: разделять выдачу сетевых параметров, передачу загрузочных файлов и разрешение имён.

## DHCP

DHCPv4 выдаёт аренду адреса и параметры: маску, шлюз, DNS, время действия. Учебная последовательность Discover, Offer, Request, Acknowledge помогает видеть, на каком шаге пропадает обмен. Серверу нужен пул в правильной подсети, исключения для статических узлов и привязка к нужному интерфейсу. Через маршрутизатор широковещание не проходит автоматически: может требоваться DHCP relay. Второй неконтролируемый сервер в сегменте создаёт конфликтующие предложения. Выбирай конкретную реализацию (например Kea) и её формат конфигурации, а не смешивай разные синтаксисы из видео и нового пакета. Проверка `kea-dhcp4 -t FILE` оценивает конфигурацию, но не заменяет рабочий обмен с клиентом.

## TFTP

TFTP — простой файловый протокол поверх UDP без встроенной пользовательской аутентификации и шифрования. Его встречают в PXE/сетевой загрузке и оборудовании. Начальный запрос использует известный порт, дальнейший обмен требует учитывать выбранные transfer ID/UDP-порты. Ограничь корневой каталог сервера и доступный сегмент, не размещай там ключи и конфигурации с паролями. Для проверки скачай заранее известный учебный файл, сравни checksum и исследуй отказ для пути вне разрешённого корня. TFTP не является безопасной заменой SCP/SFTP для обычной передачи данных.

## Роли DNS

Авторитативный сервер отвечает за свою зону, recursive resolver ищет ответы для клиента, кеширующий сохраняет результаты, forwarding передаёт запрос выбранному upstream. Один демон может совмещать роли, но политики доступа у них разные. Открытая рекурсия для всего интернета создаёт проблемы; разрешай её только нужным клиентам. Кеш может объяснить устаревший ответ до истечения TTL. NXDOMAIN означает отсутствие имени, а не поломку сети; timeout означает отсутствие ответа в пределах ожидания.

## Зона и проверка BIND

В зоне SOA задаёт служебные параметры и serial, NS — авторитативные серверы, A/AAAA — адреса, CNAME — псевдоним, MX — почту. Точка в конце полного доменного имени важна: без неё имя может получить суффикс зоны. При изменении зоны обновляй serial по принятой схеме. `named-checkconf` проверяет конфигурацию, `named-checkzone lab.test FILE` — файл зоны. Затем `dig @SERVER host.lab.test A`, `dig @SERVER lab.test SOA +norecurse` и проверка с реального клиента показывают поведение. Для больших/особых ответов DNS использует и TCP, поэтому одного разрешённого UDP/53 недостаточно для всех сценариев.

## Практический маршрут

Собери изолированный сегмент server/client. Сначала проверь статическую связность, затем аренду DHCP, затем DNS по явному адресу сервера и через настройки клиента. TFTP добавляй отдельно после работающей сети. Зафиксируй пакеты, журналы, выданные параметры и ожидаемые отрицательные проверки. При сбое не меняй одновременно три службы.
