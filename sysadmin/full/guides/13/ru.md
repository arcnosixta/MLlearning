# SSH: подключение, ключи и ограничения доступа

Цель: организовать удалённый вход по ключу и изменять настройки SSH так, чтобы сохранить проверенный путь восстановления.

## Клиент, сервер и проверка узла

`ssh user@host` запускает клиент, а соединение принимает сервер sshd. Ошибка подключения может означать отсутствие маршрута, закрытый порт, остановленную службу или отказ аутентификации: разделяй эти этапы. В учебной сети начни с `ip route`, затем проверь слушающий сокет через `ss -ltn` на сервере и используй `ssh -vv user@host` для диагностики клиента. Подробный вывод не публикуй без просмотра: он содержит имена, пути и сведения о конфигурации.

Ключ сервера в known_hosts подтверждает, к какому узлу ты подключился. Предупреждение об изменившемся ключе нельзя исправлять автоматическим отключением StrictHostKeyChecking: сначала сравни fingerprint через независимую консоль или доверенный канал. Пользовательский ключ решает другую задачу — подтверждает право пользователя войти на сервер.

## Ключевая пара и учётная запись

На своём учебном клиенте создай ключ `ssh-keygen -t ed25519`, выбрав отдельное имя файла и парольную фразу. Закрытый ключ остаётся у владельца; в authorized_keys сервера попадает только открытая часть. `ssh-copy-id -i путь.pub user@host` требует уже существующего способа входа. На Linux проверь владельца домашнего каталога, `.ssh` и authorized_keys, затем права через `namei -l` и `stat`: доступ на чтение одного файла не исправит неправильного владельца родительского каталога. ssh-agent временно предоставляет возможность подписи; не включай agent forwarding без понятной необходимости.

## Ограничения и безопасная смена конфигурации

В конфигурации сервера явно определи допустимые учётные записи, вход root, парольный и ключевой способы. `PasswordAuthentication no` не описывает все возможные интерактивные механизмы: учитывай KeyboardInteractiveAuthentication и PAM. Ограничение по IP на firewall и ограничения OpenSSH дополняют друг друга, но применяются в разных слоях. Match-блоки и включаемые файлы меняют эффективные настройки; проверяй результат, а не только найденную строку.

Работай через отдельную VM с доступом к консоли. Сохрани исходный файл, выполни `sshd -t`, а эффективную конфигурацию исследуй через `sshd -T` с нужным контекстом подключения. Не закрывая первую сессию, примени штатный reload службы для своего дистрибутива и открой вторую сессию по ключу. Только после успешной проверки отключай запасной способ входа. При отказе откати файл через консоль. Смена порта уменьшает шум, но не заменяет аутентификацию.

### 2. Отказ ключа

Клиент предлагает правильный ключ, но сервер отказывает. Построй план диагностики без chmod 777.

{{answer:2}}

<details><summary>Подсказка и решение</summary>

Проверь имя пользователя, authorized_keys и его содержимое, владельца и доступ по всему пути, эффективные настройки sshd, серверный журнал и разрешённые алгоритмы. Исправляй конкретную причину; широкие права могут сами вызвать отказ StrictModes.
</details>

### 3. Изменившийся host key

Сервер после переустановки показывает новый ключ. Как отличить ожидаемую замену от подмены?

{{answer:3}}

<details><summary>Разбор и самопроверка</summary>

Получай fingerprint с консоли нового сервера и сравнивай вне спорного соединения. Только после подтверждения обнови соответствующую запись known_hosts. Чем host key отличается от пользовательского ключа? Почему первая рабочая сессия не доказывает работоспособность нового входа?
</details>
